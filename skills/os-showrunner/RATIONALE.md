# Rationale: os-showrunner

Why this skill is shaped the way it is. Not loaded by the skill and nothing points here.

- **Its own skill.** Rob's framing: agentware is the show, the showrunner is the person making it happen. The previous version fused the two, so the role could not be invoked without dragging the system-building doctrine in. A lieutenant is this skill with a narrower brief, so it gets no skill of its own.
- **Workers can write.** The previous version's "single writer, workers only report" was architecture. The supercar-game lanes, with thirty agents committing to one checkout in a day, showed that coordination through files on shared main works when a few tree rules are in the project's instructions. Those rules are in `delegation.md`; the single-writer stance is not.
- **State is trimmed, not append-only.** Rob's ruling that files which only ever grow bloat the context. `project-state.md` carries the archive discipline and makes the decisions file optional.
- **The cold reader and surveyor are offered, not required.** Both are genuinely useful from clean context and both were gates in the previous version. They live in `briefs/` as things to reach for.
- **The unattended reference keeps the failure stories.** Each rule there was paid for on a real run (the stop-condition grep that missed bold text, the lock trap, the prompt that carried the weakest rules list). The stories are what make the rules believable to a fresh reader, so they stayed.
- **Companionship is in the skill body, not a persona.** The doctrine names the showrunner as a creative partner who celebrates wins and keeps momentum. That is written as how to work with the operator, not as a character to perform, because performed personality drifts and spends attention.
